# Database Baseline

Every stack which materializes the checked Managed PostgreSQL contract must set
exactly one `aws:allowedAccountIds` value. The value is intentionally unknown
until the Organizations stack returns the real workload account ID; this is a
hard provider guard, and the canonical claim compiler rejects an omitted,
placeholder, or multi-account target before resource planning.

The generic `database` module can deploy Aurora PostgreSQL or MySQL. A checked
`ManagedPostgres` intent is stricter: materialization fails before Pulumi unless
the provider config is Aurora PostgreSQL, the exact requested major/port and
supported extensions match, end-to-end IAM RDS Proxy is enabled, retention is
sufficient, and an explicit regional recovery-copy target exists.

## Posture

- Private subnet placement only; no `publiclyAccessible` instances.
- Storage encryption with a per-cluster customer-managed KMS key (rotation +
  30-day deletion window). Enforced by Pulumi policy
  `rds-clusters-private-and-protected`.
- IAM database authentication enabled. RDS generates and rotates the master
  credential in Secrets Manager under the cluster KMS key; no password value is
  generated by this module or stored in Pulumi state.
- Deletion protection on by default. The mandatory policy pack rejects
  `deletionProtection: false`.
- Backup retention >= 14 days (35 in the platform-prod example), copy-tagged
  for AWS Backup, and PITR enabled by default through Aurora.
- `replicationRequired` on the neutral data boundary compiles on AWS to an
  immutable cross-region AWS Backup copy, not an Aurora read replica. The
  provider plan names this `regionalRecoveryCopy` so the IaC does not claim a
  replication mechanism it does not create.
- Multi-AZ via at least two cluster instances. The validator rejects
  `instanceCount < 2`.
- Performance Insights with KMS encryption and 731-day retention so forensics
  go back two years.
- CloudWatch logs export: `postgresql` for Aurora PostgreSQL, audit + error +
  general + slow-query for Aurora MySQL.
- A parameter group that turns on `pgaudit`, forces SSL, and logs DDL/slow
  statements (or `server_audit_logging` for MySQL).
- Optional RDS Proxy with `requireTls` and end-to-end IAM authentication. The
  proxy role is scoped to the exact runtime and migration database users on
  this cluster and has no wildcard user or Secrets Manager access. Mandatory
  policy pack rejects RDS Proxies without TLS.
- Proxy clients receive wildcard-free `rds-db:connect` policies for the exact
  Proxy resource ID (`prx-...`) and PostgreSQL login. The cluster resource ID
  is reserved for direct-cluster access and the separate Proxy-to-database role;
  target/resource-ID substitutions fail compilation.
- No VPC-CIDR database ingress. The module creates separate runtime, migration,
  bootstrap, proxy, and cluster security groups. Runtime and migration reach
  only the Proxy; the Proxy reaches the cluster; the isolated bootstrap group
  reaches the cluster directly because the end-to-end-IAM Proxy cannot accept
  the RDS-managed master password. Every path is SG-to-SG and port-exact.
- Rootless provisioning uses a dedicated `database` capability lane. Every IAM
  role has a deterministic `${resourceNamePrefix}-database-*` name and the
  exact delegated-role boundary compiled from the checked bootstrap access
  plan. The human-operated database apply lane has a different mutation-only boundary and
  cannot log in to PostgreSQL, read/decrypt the master secret, or publish RDS
  monitoring logs.
- RDS create calls require `ManagedBy=pulumi`, the exact organization tag, and
  the lane-owned `Name` prefix. Existing-resource mutations require the same
  ownership tags, account, and allowed Region. Ownership tag removal and
  cross-account/Region mutation fail closed. These controls follow AWS's
  [RDS action/resource/condition model](https://docs.aws.amazon.com/service-authorization/latest/reference/list_amazonrds.html)
  and the documented recommendation to protect tags used for authorization.

## Stack config

`Pulumi.platform-prod.yaml.example` now includes:

```yaml
secure-saas-infra:awsBootstrapAccessPlanPath: contracts/aws-bootstrap-access-v1alpha1.json
secure-saas-infra:awsBootstrapAccessAccountName: platform-prod
secure-saas-infra:database:
  name: control-plane
  engine: aurora-postgresql
  engineVersion: "16.4"
  engineMajorVersion: "16"
  databaseName: deus
  masterUsername: deus_admin
  port: 5432
  instanceClass: db.r6g.large
  instanceCount: 2
  backupRetentionDays: 35
  deletionProtection: true
  createProxy: true
  replicaRegion: us-west-2
```

`validateDatabaseConfig` rejects `engine` values outside
`aurora-postgresql`/`aurora-mysql`, `deletionProtection: false`,
`backupRetentionDays < 14`, `instanceCount < 2`, and out-of-range `port`.

## Codefly and authentication boundary

This module publishes reference-only endpoint, Region, database, user, Proxy
resource ID, cluster resource ID, identity, network, CA, and bootstrap-secret
metadata. It never publishes a password or IAM authentication token.

Codefly owns PostgreSQL role reconciliation and migrations. Its managed AWS
client must use the Pod Identity default credential chain and generate a fresh
RDS IAM token immediately before every new physical pool connection. A token is
valid for only 15 minutes and must never be stored in configuration, a
Kubernetes Secret, an environment variable, a log, or Pulumi state. See the
[full PostgreSQL/Codefly/AWS ownership decision](postgres-codefly-aws-auth-boundary.md).

IaC creates one isolated bootstrap role/policy plan with exact access to the
RDS-managed master secret through one Secrets Manager VPC endpoint and the
constrained KMS decrypt path. It does not create a standing bootstrap Pod
Identity association. A future authorized infrastructure operation activates
that association just in time for role/grant/RLS reconciliation and removes it
after evidence is observed. Runtime and migration identities cannot read the
secret.

For EKS Auto Mode, IaC emits one dedicated `NodeClass`/`NodePool` pair per
runtime, migration, or bootstrap access class. The NodeClass selects the exact
private Pod subnets and class-specific security group. The NodePool uses a
unique label and `NoSchedule` taint, and the exported binding supplies the exact
selector/toleration that an admitted workload must copy. A cluster-wide
fail-closed policy reserves that selector for the access class's exact
namespace, requires runtime Pods to be owned by Deployment-managed ReplicaSets
and migration/bootstrap Pods by Jobs, and rejects incompatible workload kinds.
The NodeClass disables SNAT so Pod traffic retains the Pod security-group
boundary; real AWS validation must still prove routes and return paths. This is
the supported Auto Mode replacement for VPC CNI `SecurityGroupPolicy`, which
Auto Mode does not support.

The stack exports application-safe, runtime-only `databaseBindings`,
`databaseAccessBindings`, and checked `postgresAccessProfiles` separately from
deploy-control-only `databaseMigrationBindings`,
`databaseMigrationAccessBindings`, and `postgresMigrationAccessProfiles`.
Controller-only `databaseInfrastructureHandoffs` contain the Namespace,
ServiceAccount, fail-closed admission policy, `ApplicationNetworkPolicy`,
NodeClass, and NodePool. All v1alpha1 profiles remain
`pending-infrastructure`; they cannot claim readiness.

The handoff is itself a checked, content-addressed v1alpha1 contract. Each
provider manifest bundle remains opaque to the generic envelope but is bound by
its exact SHA-256 digest; the AWS materializer additionally validates namespace,
ServiceAccount, binding annotation, and full typed manifest shape before export.
Readiness is represented separately by checked
`PostgresAccessObservationEvidence v1alpha1`: Ed25519-signed, expiring,
revocable, replay-protected evidence binding the profile/handoff digests,
resource UIDs/versions/spec digests, controller/source/RBAC denial evidence,
and PostgreSQL bootstrap state. A verified observation yields an ephemeral
ready decision and never rewrites the immutable pending profile.

## Operating

- Reserve the RDS-managed master credential for the isolated bootstrap/grant
  reconciler and audited break-glass administration. Applications and
  migrations authenticate with dedicated IAM database users; they never receive
  the master credential.
- Use the RDS Proxy endpoint for application connections so connection bursts
  are absorbed and database connection budgets are protected.
- Apply the emitted runtime and migration handoffs through the authorized
  infrastructure-controller/GitOps lane, then copy the matching labels,
  annotations, selector, and toleration into only the corresponding workload.
  Activate bootstrap only just in time. Creating source groups or exporting a
  manifest is not runtime proof; AWS-dev must confirm API admission,
  `ApplicationNetworkPolicy`, dedicated Auto Mode placement, the Pod ENI's
  exact group, Pod Identity, STS, TLS, and RDS Proxy connectivity.
- Tag the cluster with `Backup=required`; AWS Backup picks it up via the
  selection from the `backup` stack.
- Monitor `RDSDeletionProtection` and `RDSStorageEncrypted` Config rules from
  the compliance conformance pack.
